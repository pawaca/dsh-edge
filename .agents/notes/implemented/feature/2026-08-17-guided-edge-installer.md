# Agent Note: Install dsh-edge through one guided command

Status: implemented

English | [中文](2026-08-17-guided-edge-installer.zh.md)

The post-upload success boundary is refined by [handing off Edge installs without CLI probing](../simplification/2026-08-18-edge-install-handoff-without-probing.md).

## Problem

A personal `dsh-edge` instance needs a Worker, two secrets, one of two runtime configurations, a Cloudflare account choice, and a safe handoff of the deployed target and access details. Exposing those as separate dashboard and Wrangler procedures makes Free and isolated installs diverge, risks placing secrets in shell history, and makes Cloudflare Builds plus a bound source repository look like product requirements even though neither participates at runtime.

The Free runtime can also use Wrangler's temporary preview accounts. Requiring account registration before the user has tried the product removes that advantage, while offering temporary accounts for the Worker Loader configuration would fail because that resource is unsupported there.

## Decision

Platform interpretation: the mode-`0600` guarantee below applies to POSIX hosts. On Windows, Node exposes synthetic POSIX mode bits rather than the inherited NTFS ACL, so the per-installation files instead inherit the current user's temporary-directory ACL. Both platforms remove the credential file, private configuration, and containing temporary workspace before reporting success.

`dsh-edge install` is the user-facing operation, with `install:cloudflare` as the source-checkout entry. It selects the runtime first. `Free — Direct Shell` accepts a temporary account, a detected account, or browser sign-in and registration. `Isolated — Dynamic Worker` omits temporary accounts and states that it requires Workers Paid, which is separate from the Cloudflare Pro website plan. Cloudflare remains authoritative for the account's Worker Loader entitlement because Wrangler exposes no reliable preflight query for it.

The installer then selects an exact Worker name and checks for an existing deployment. It requires an explicit update choice before reusing a name. Account metadata parsed from Wrangler must be non-empty and free of C0, DEL, and C1 terminal control characters before it can enter a prompt label, option value, or child environment. The installer generates a random owner access key by default, accepts hidden custom input under the runtime's byte contract, and collects the DeepSeek key through hidden input. A confirmation summarizes runtime, account, Worker name, and cost before upload. The temporary path separately presents Cloudflare's Terms of Service and Privacy Policy and requires explicit acceptance.

Wrangler receives both credentials through a private mode-`0600` temporary secrets file. Every Wrangler subprocess receives an explicit allowlist of operating-system, terminal, locale, proxy and certificate variables, plus only the Cloudflare authentication inputs selected for that command; unrelated ambient credentials and Node injection options are excluded. Temporary installs also remove Cloudflare credential and configuration sources and use an isolated Wrangler configuration directory, so an existing local login cannot capture the deployment. Structured Wrangler output supplies the public Worker target and release metadata; both captured diagnostics and the metadata file are limited to 2 MiB of valid UTF-8 before parsing. Interactive authentication output remains visible, while deployment output is captured behind one progress indicator unless the user selects `--verbose`. Interactive stdout and stderr pass through independent chunk-safe terminal filters before forwarding: only plain text, tab, newline, and carriage return remain, while every SGR/ANSI sequence, C0/C1 control, Unicode bidirectional control, OSC string, cursor command, and other escape sequence is removed. Account labels, identifiers, email metadata, claim URLs, and displayed owner access keys reject the same terminal-spoofing controls. Each child stream pauses until a slow destination drains; a synchronous write failure, asynchronous `EPIPE`, or early destination close terminates and joins the Wrangler process tree, then rejects through the installer's normal credential-cleanup path. The same managed output boundary remains around Clack prompts, recovery cards, and final status until private-directory cleanup completes. It tracks asynchronous writes and early close or error; signal interruption destroys a blocked stdout destination rather than merely releasing wrapper callbacks, then routes post-upload recovery through the opposite managed stream. Non-deployment commands such as interactive authentication reject an output failure even when Wrangler exits with status 0; only deployment retains that paired outcome for credential recovery. Captured diagnostic text passes through the same plain-text filter before it enters an installer error. A rejected upload is reported as not installed; a temporary account claim URL remains recoverable, but the unused owner key is not presented as active. The installer makes no request to the resulting target; it accepts only a credential-free root HTTPS origin under `*.workers.dev` from structured output, then hands that URL and the owner key to the user. It removes temporary files on success, failure, or process interruption before printing success, then rechecks interruption after the awaited cleanup boundary. If final directory cleanup fails after a successful upload, the installer prints recovery details and fails without first claiming success; if cleanup also fails behind another error or interruption, it warns separately and preserves that primary error and exit semantics. If Wrangler has already uploaded the Worker but credential cleanup, output forwarding, output parsing, claim validation, or interruption prevents success, a recovery card prints the now-active owner key and any known URLs before the command exits with the original failure. When one output stream caused the failure, this card bypasses Clack and is queued through the opposite managed output boundary. Delivery is recorded only after the destination's asynchronous write callback succeeds; after an output failure, the surviving stream receives a bounded drain window before a remaining blocked write is canceled. Failure of that alternate stream is contained so directory cleanup still runs. Wrangler exit status, output failure, and concurrent abort state remain independent, so a status-0 close still reaches this recovery path before the interruption or output failure is reported. SIGHUP, SIGINT, and SIGTERM cancel a pending prompt or terminate Wrangler through Execa's managed descendant-tree spawn while preserving exit statuses 129, 130, and 143 respectively: POSIX uses an isolated process group with SIGTERM-to-SIGKILL escalation and an explicit group-liveness join; Windows awaits `taskkill /T /F`. Cleanup starts only after this tree is quiescent. A temporary install also requires and prints Wrangler's bearer claim URL with its 60-minute retention deadline.

Release packaging builds direct and isolated Worker artifacts from the tested workspace sources. The npm package treats the Harness, Computer, and just-bash packages as build-time dependencies; the installer selects one released artifact and uploads it with Wrangler `no_bundle`, so an npm consumer cannot accidentally rebuild the Worker from separately published upstream packages. The install uploads directly from the prepared package or checkout. It does not create or bind a GitHub repository, Cloudflare Builds project, or source-build pipeline.

## Alternatives considered

- **Cloudflare Builds as the primary setup:** automatic builds are useful for contributors, but a repository binding and build variables are unrelated to operating one personal instance.
- **One command per runtime:** this makes the mode choice less visible and allows account, secret, and handoff behavior to drift between two entry points.
- **Require Cloudflare login:** this simplifies authentication handling but loses the Free runtime's temporary-account trial path.
- **Pass secrets through command arguments or inherited environment variables:** both can leak through process inspection, shell history, diagnostics, or an unintended credential source.
- **Infer Workers Paid before upload:** Wrangler account metadata does not establish Worker Loader entitlement, so a local guess would reject valid accounts or promise an upload that Cloudflare later rejects.

## Consequences

- A user makes the cost and isolation choice before Cloudflare account selection. Temporary installation remains a Free-only path, while isolated installation fails with an actionable Workers Paid or direct-mode choice.
- Existing Workers retain their Durable Object data when explicitly updated. Different Worker names isolate the direct and isolated modes without duplicating application code or configuration ownership.
- The DeepSeek key and both secret values stay out of command arguments and progress output. The owner key is printed after a successful install, or in a post-upload recovery card when the upload is active but handoff cannot complete; the DeepSeek key is never echoed.
- Installer success means Wrangler accepted the upload and supplied an admitted `workers.dev` target. Runtime health remains available as an explicit diagnostic rather than an installation prerequisite.
- Installation has no source-hosting dependency or user-side application build. Publishing produces the deployable Worker artifacts; the installation contract remains `dsh-edge install` and a direct Wrangler upload.
