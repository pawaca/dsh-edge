# Agent Note: dsh-edge 0.3 vision roadmap

Status: `0.3.0-alpha.1` published — `0.3.0-alpha.2` corrective upgrade UX ready for review

English | [中文](2026-08-21-dsh-edge-v0.3-vision-roadmap.zh.md)

## Outcome

dsh-edge 0.3 upgrades its exact DeepSeek Harness baseline from `0.1.0-rc.8` to `0.1.1-rc.1`, exposes the three models owned by the published DeepSeek adapter, and makes the upstream image-attachment experience work on Cloudflare. A new permanent authenticated deployment stores immutable image bytes in a private R2 bucket. An unauthenticated temporary deployment uses a deliberately bounded Durable Object fallback because Cloudflare temporary accounts do not support R2. A Worker created before image support has no attachment references, so its first 0.3 upgrade may choose either backend before that choice becomes pinned.

The release also replaces the root README's reference-manual opening with a product-first landing page: a concrete promise, the problem it solves, a real screenshot, and the install command must all be understandable before the implementation details.

## Non-negotiable ownership boundary

For every capability, use this order and record why a lower choice was necessary:

1. Consume the published upstream package, plugin, UI, protocol, schema, and default catalog unchanged.
2. Compose an upstream service/provider/plugin slot.
3. Implement the smallest Edge-owned adapter behind an upstream interface.
4. Add an `ui-edge` contribution only for Cloudflare-specific product state or actions.
5. Apply an exact-version package patch only when composition cannot express the requirement.
6. Never copy or independently reimplement an upstream product capability.

An upstream model or attachment schema remains the source of truth. Storage selection, Cloudflare provisioning, owner authentication, and deployment diagnostics are dsh-edge responsibilities. Every delivery PR must answer:

- Which upstream capability is reused?
- Why is each new Edge-owned code path not expressible by composition alone?
- Did the PR add or retain a package patch, and what removes it?

## Scope

### Included

- Exact upstream baseline `0.1.1-rc.1`.
- Upstream DeepSeek catalog entries for V4 Flash, V4 Pro, and V4 Flash Vision Exp.
- Upstream model-selection UI and session model protocol.
- Upstream image composer, preview, history gallery, lightbox, wire types, session `ImageBlock`, admission vocabulary, and provider conversion.
- An Edge implementation of upstream `AttachmentStore`.
- Private R2 object storage for new permanent-account installations.
- A bounded Durable Object attachment backend for temporary-account previews.
- A one-time R2-or-DO choice when a pre-attachment Worker first upgrades to 0.3.
- Installer and Edge diagnostics for the selected attachment backend.
- A product-first English and Chinese root README with real product media.

### Excluded

- Generic files, audio, video, assistant-generated images, and public attachment URLs.
- Reference-aware garbage collection, which upstream also defers because resumed and forked sessions can share immutable objects.
- Automatic migration from a claimed temporary deployment's DO attachment backend to R2. Claiming preserves the DO backend; a future explicit migration must not strand existing references.
- `web_fetch`, `@file`, `@session`, additional providers, and unrelated upstream features.
- A second model catalog, attachment schema, composer, gallery, or provider request serializer owned by dsh-edge.

## Stage 0 evidence

### Published baseline

- The audited upstream tag is [`dsh-v0.1.1-rc.1`](https://github.com/deepseek-ai/deepseek-harness/tree/dsh-v0.1.1-rc.1), commit `528c682e061696f5a160f363f236ecbf53cbd006`.
- The relevant `@deepseek-ai/dsh-*` packages are publicly available at exact version `0.1.1-rc.1`; implementation work must consume those artifacts, not the upstream checkout.
- `SESSION_FORMAT_VERSION` remains `0` in rc.8 and rc1. Image messages add upstream `ImageBlock` values without requiring an Edge session-format fork.

### Models and provider path

- `@deepseek-ai/dsh-llm-deepseek` owns the default catalog. Omitting a custom `models` array exposes, in order, `deepseek-v4-flash`, `deepseek-v4-pro`, and image-capable `deepseek-v4-flash-vision-exp`.
- The current Edge adapter suppresses that upstream catalog with `models: []`; Stage 1 removes that suppression instead of maintaining a local list.
- The upstream `DeepSeekAdapter` already accepts a `resolveAttachments` hook. It resolves durable image references, verifies bytes through `AttachmentStore`, converts them to transient data URLs, rejects image input for text-only models, and enforces the upstream 20 MiB request-image budget. dsh-edge must not duplicate this serializer.
- Existing request-scoped credentials remain compatible: the Edge adapter binds the API key for an active turn and can provide attachments through the same operation-local adapter construction without persisting either secret or bearer material.
- On 2026-08-21, a real non-streaming request to `https://api.deepseek.com/chat/completions` using `deepseek-v4-flash-vision-exp` returned HTTP 200 and identified the upstream deterministic 1×1 red PNG as `Red`. The temporary test key was supplied only to the process and was not written to disk or this note.
- The official [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/) and [Create Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion) pages still list only Flash and Pro. Therefore 0.3 labels Vision Exp as experimental and reports provider rejection honestly instead of claiming universal account availability.

### Attachment path

- `@deepseek-ai/dsh-attachment` is the upstream seam. `AttachmentStore` owns `imageLimits`, `validateImage`, `saveImages`, `saveImage`, and `readImage`; `admitEncodedImages` owns canonical base64 and batch admission.
- Upstream references are immutable, content-addressed `sha256:` identifiers with verified media type, byte length, width, height, and optional display name. Session events persist only those references, never paths, object URLs, provider URLs, or base64.
- `@deepseek-ai/dsh-client-ui-conversation` owns paste/drop intake and consults the `imageLimits` projection. `@deepseek-ai/dsh-client-ui-attachment` owns the draft rail, drop overlay, history gallery, and lightbox. The rc1 Web roster already includes the attachment plugin; dsh-edge currently excludes it and must stop doing so once the backend is composed.
- The upstream API owns the `session.attachment` wire shape, session-reference authorization rule, model-modality preflight, and `imageLimits` projection. Because dsh-edge already owns a Cloudflare-specific `ApiProxy`, it must implement this existing contract as thin wiring, using upstream types, errors, and admission helpers rather than creating new routes or payloads.
- `@deepseek-ai/dsh-attachment-local` cannot run in Workers: it depends on Node filesystem and crypto APIs plus native `sharp`. Stage 2 implements the upstream seam instead of patching the local backend. Worker-compatible full image validation and its Direct bundle-size effect are the main implementation risks to prove before enabling upload.

### Storage selection

- R2 is the canonical permanent binary backend: object keys derive from the upstream SHA-256 attachment identity; buckets stay private and are accessed only through a Worker binding. DO state continues to hold session events and their upstream references.
- Cloudflare gives R2 Standard an included monthly tier, but requires a permanent Cloudflare account with an R2 subscription. See [R2 getting started](https://developers.cloudflare.com/r2/get-started/) and [R2 pricing](https://developers.cloudflare.com/r2/pricing/).
- Cloudflare's [temporary-account supported-resource list](https://developers.cloudflare.com/workers/platform/claim-deployments/#supported-resources) includes Workers, Static Assets, KV, D1, Durable Objects, Hyperdrive, Queues, and certificates, but not R2. A temporary install therefore cannot make R2 a mandatory dependency.
- KV is not the fallback because attachment upload is followed by immediate model read, while Workers KV does not guarantee read-after-write visibility and can take 60 seconds or more to propagate. See [How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/#consistency).
- The temporary DO backend is intentionally a preview fallback, not the long-term object architecture. Its limits must be conservative, must never exceed upstream admission limits, and must be visible in Edge diagnostics.

### rc1 patch disposition

| rc8 patch | Stage 0 disposition |
| --- | --- |
| `dsh-client-ui-conversation` image gating | Rebase and retain until every deployment composes `AttachmentStore` and `imageLimits`; remove in Stage 3 when temporary previews gain their bounded backend, or when upstream publishes the same capability gate |
| `dsh-client-ui-workspace` delete capability | Rebase and retain unless the rc1 upgrade proves an upstream equivalent; rc1 published code does not contain the required capability gate |
| `dsh-host-apiproxy` Worker crypto | Re-audit against the actual Worker bundle; rc1 still imports `node:crypto` and has more UUID call sites, so the rc8 patch cannot be carried mechanically |
| `dsh-llm` attribution manifest | Rebase and retain unless bundle tooling can consume the exported JSON without runtime `node:module`; rc1 still uses `createRequire` |
| `dsh-session-persistence` bounded read and abandonment | Rebase and retain; rc1 does not publish equivalent coordinator APIs required by the Edge persistence adapter |
| `dsh-web-search-deepseek` redirect handling | Rebase and retain; rc1 still uses `redirect: "error"`, which is not the validated Worker behavior |

No new patch is justified by the Stage 0 audit. The rc1 baseline retains six rebased patches, including the conversation capability gate while temporary previews have no attachment backend. Stage 3 may remove that patch only when image admission is available in every deployment. Bundle evidence may remove more, but may not silently broaden one.

## Stage 1 evidence

- The complete standalone and `ui-edge` dependency closure is pinned to exact `0.1.1-rc.1`; root and standalone lockfiles contain one Harness version.
- Edge now calls the upstream DeepSeek `resolveAdapterOptions` and exposes its unchanged catalog: `deepseek-v4-flash`, `deepseek-v4-pro`, and `deepseek-v4-flash-vision-exp`. No Edge model list was added.
- The published upstream model-selection client plugin is part of the reviewed 30-plugin Web graph. Edge's existing Cloudflare `ApiProxy` projects the upstream LLM registry into the upstream `session.models`, `session.selectModel`, and `llm.models` contracts.
- The upstream `ModelSelectionRef` remains the Agent seam. One adapter-owned Durable Object KV record preserves an accepted pre-turn session selection across hibernation, then is transactionally retired after the matching canonical `request/header` event is durably flushed. The upstream event remains the durable source after a turn, and no upstream session table or event schema changed.
- The rc1 structured boot protocol is assembled with the published upstream `bootInjections`, `orderByModuleGraph`, and `renderIndexInjections` functions rather than an Edge copy.
- All six retained patches were rebased exactly to rc1. The host crypto patch covers rc1's expanded UUID call sites; no new patch was added. Image intake remains gated whenever the host omits `imageLimits`.
- Validation passed: 211 unit tests, typechecks and lint; deterministic standalone assembly; 30-plugin boot contract; browser snapshots; Direct and Isolated release-artifact integrations; existing released durable-state fixtures; Flash and Pro text paths; three-model discovery; and model selection before and after canonicalization across Worker restarts. The Direct artifact is 690,801 gzip bytes against its 921,600-byte budget.

## Stage 2 evidence

- Edge implements the published upstream `AttachmentStore` seam over private R2. Object keys derive from the upstream `sha256:` identity; R2 holds immutable raw bytes while canonical session events hold unchanged upstream image refs. No Edge attachment schema, public URL, composer, gallery, or provider serializer was added.
- The existing Edge `ApiProxy` now wires upstream `admitEncodedImages`, error vocabulary, model-modality preflight, `imageLimits`, session-reference authorization, and `session.attachment`. The request-scoped upstream `DeepSeekAdapter` receives only a resolver that calls the composed store, so provider data-URL conversion stays upstream-owned.
- New permanent installs create or reuse a deterministic private R2 bucket and add its binding only to the generated deployment config. Failed upload never deletes it. Missing R2 produces an actionable activation/retry error. Temporary previews deliberately omit `imageLimits` until Stage 3 supplies the same seam over a bounded DO backend.
- Worker-side admission fully decodes PNG and JPEG, checks declared type, dimensions, pixels, bytes, aggregate count and size, and advertises only those two proven formats. The accepted limits are 4 images per message, 3.5 MiB per image, 7 MiB aggregate, 40 million pixels, and 2,000 pixels per side.
- The standalone attachment-plugin exclusion was removed, so the deterministic upstream Web graph contains all 31 plugins. The existing exact-version conversation capability patch remains one of six patches: it leaves the upstream attachment UI enabled when `imageLimits` is projected and blocks paste/drop only in temporary previews that lack a backend. Browser coverage proves both paths, draft admission, history image rendering, and the upstream Vision model label.
- Validation passed: 217 runtime unit tests, typecheck, browser/install/model snapshots, deterministic standalone assembly, Direct and Isolated release-artifact integrations with local R2, authorized and cross-session reads, multi-page cold-history image predicates, model-selection/admission serialization, temporary-preview intake gating, fork reuse, restart persistence, corruption rejection, cancellation, and install-from-tarball smoke checks. The Direct artifact is 709,714 gzip bytes against its 921,600-byte budget.

## Stage 3 evidence

- Deployments without `DSH_EDGE_ATTACHMENTS` now compose the same published upstream `AttachmentStore` over an Edge-owned Durable Object byte backend. The session log, image refs, `ApiProxy`, upstream client plugins, and provider serializer remain backend-blind.
- Temporary objects are immutable and content-addressed, split into 512 KiB SQLite BLOB rows, written one upload batch at a time with metadata and quota accounting in a synchronous transaction, and verified again on read. Unique objects in a rejected batch leave no partial data or consumed quota. One owner instance has a 64 MiB application limit while retaining the same PNG/JPEG message-admission limits as R2. This stays below Cloudflare's current [2 MiB SQL row/BLOB limit and Workers Free 5 GB account allowance](https://developers.cloudflare.com/durable-objects/platform/limits/).
- The first initialized owner Durable Object pins `temporary-do` or `private-r2` in Edge-owned state. Generated deployments also carry an explicit storage marker. The installer inspects every active Worker version before an update, preserves its marked or bound choice, and refuses mixed rollouts. An unmarked release with no attachment binding predates image support and therefore has no image refs; its first 0.3 upgrade asks once between the 64 MiB DO backend and private R2, then writes the selected marker. Claiming a temporary account and later upgrading cannot silently move old refs to an empty R2 backend; a pinned R2 deployment fails closed if its binding disappears. Automatic migration remains explicitly out of scope.
- Temporary installer summaries now advertise bounded instance storage. The authenticated read-only composition reports the actual pinned backend and its DO storage cap, while public health reports the deployment-configured default without waking Durable Object state.
- The obsolete conversation capability patch was removed. The deterministic 31-plugin upstream Web graph now uses the published conversation image intake unchanged, reducing the exact-version patch set from six to five.
- Validation passed: 242 unit tests and typechecks; browser, installer, model, Direct temporary-DO, and Isolated private-R2 integration snapshots; deterministic standalone assembly; and install-from-tarball verification of both promoted artifacts. Coverage includes atomic batch quota rollback, chunking, deduplication, integrity, backend pinning, legacy upgrade selection, upstream browser draft UI, model request, history, fork, and Worker restart. The Direct artifact is 711,855 gzip bytes against its 921,600-byte budget.

## Stage acceptance details

### Stage 1 — baseline and models

- Pin the complete standalone and `ui-edge` dependency closure to exactly `0.1.1-rc.1`.
- Rebuild the upstream client graph; accept upstream roster changes unless an Edge capability is genuinely absent.
- Remove `models: []` and source model metadata from the upstream adapter catalog.
- Make the existing Edge `session.models` and `session.selectModel` implementation expose and select upstream results without a second catalog.
- Keep the image upload affordance disabled until an attachment service and authoritative `imageLimits` are composed.
- Pass deterministic assembly, Direct size, both runtime integrations, browser snapshots, package installation, and rc8 durable-state fixtures.

### Stage 2 — upstream attachments over R2

- Implement one Edge `AttachmentStore`; reuse upstream IDs, refs, limits, `AttachmentError` codes, `admitEncodedImages`, UI, projection, wire payloads, authorization semantics, and DeepSeek conversion.
- Store raw immutable bytes in a private R2 bucket and no image bytes in session events.
- Prove server-side raster type/dimension/pixel validation in Workers without trusting browser metadata and without breaking the Direct gzip budget.
- Prove upload, prompt, authorized history read, refresh, restart, fork/replay semantics, corruption rejection, cancellation, and credential non-persistence.
- Installer creates or reuses the bucket only for an authenticated account whose R2 subscription is available; failures explain the exact recovery action.

### Stage 3 — temporary fallback

- Implement the same `AttachmentStore` contract over bounded DO chunks only for deployments without an R2 binding.
- Storage selection is deployment-level and invisible above the attachment seam.
- Claiming a temporary deployment preserves its DO data and backend. An authenticated upgrade must not silently switch storage and strand history.
- Diagnostics state `R2` or `Temporary DO`, limits, claim consequences, and the path to a future explicit R2 migration.
- Anonymous installation completes one real image turn without Cloudflare login.

### Stage 4 — README and release

The root README follows the product-first information hierarchy demonstrated by [Wake](https://github.com/iAmCorey/Wake): badges, one concrete sentence, the user's problem and the product's answer, real product media, then features and installation. Architecture belongs later or in the runtime reference.

The first viewport must answer in about ten seconds:

- What is dsh-edge?
- Why is it useful compared with running Harness locally?
- Can I try it without a server, repository, or existing Cloudflare account?
- What command starts the installation?

Required README order:

1. Name, release/npm/license/CI badges, and independent-community status.
2. Product promise: “DeepSeek Harness in your browser, deployed to your Cloudflare account with one command.”
3. One concrete problem/solution paragraph and an actual screenshot or short optimized animation.
4. The install command and the temporary-versus-permanent distinction. While 0.3 is a prerelease, the primary command is `npx dsh-edge@next install` and the stable `npx dsh-edge install` path remains visible.
5. User outcomes: anywhere access, own key/data, Web Search, workspace/shell, three models, and experimental image understanding.
6. Runtime and attachment-storage choices, security, limitations, upgrade, then development and architecture.

English and Chinese carry equal authority. Product claims must match tested behavior; the README must say that temporary deployments expire unless claimed, new permanent installs require R2 activation, a legacy Worker may choose bounded DO storage on its first 0.3 upgrade, and Vision Exp availability may depend on the provider account.
