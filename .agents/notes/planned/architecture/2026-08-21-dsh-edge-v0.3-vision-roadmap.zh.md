# Agent Note：dsh-edge 0.3 视觉能力路线图

状态：进行中——阶段 2 已完成

[English](2026-08-21-dsh-edge-v0.3-vision-roadmap.md) | 中文

## 目标结果

dsh-edge 0.3 将精确锁定的 DeepSeek Harness 基线从 `0.1.0-rc.8` 升级到 `0.1.1-rc.1`，展示已发布 DeepSeek adapter 自己维护的三款模型，并让上游图片附件体验可以在 Cloudflare 上运行。通过永久账号认证安装的实例把不可变图片字节存入私有 R2 Bucket；匿名临时安装则使用有意限制容量的 Durable Object fallback，因为 Cloudflare 临时账号不支持 R2。

这个版本还会把根 README 从“参考手册式开场”改造成产品首页：具体的价值承诺、用户问题、真实截图和安装命令，都必须在实现细节之前被用户理解。

## 不可妥协的所有权边界

每项能力必须依次采用下面的实现方式，并记录为什么需要降到下一层：

1. 原样消费上游已发布的 package、插件、UI、协议、schema 和默认 catalog。
2. 组合上游 service/provider/plugin slot。
3. 在上游接口后面实现最小的 Edge adapter。
4. 只有 Cloudflare 特有的产品状态或操作才新增 `ui-edge` 贡献。
5. 只有组合无法表达需求时，才应用精确绑定版本的 package patch。
6. 绝不复制或独立重写上游已有的产品能力。

上游模型与附件 schema 始终是真源；存储选择、Cloudflare 资源创建、owner 认证和部署诊断属于 dsh-edge。每个交付 PR 都必须回答：

- 复用了哪项上游能力？
- 每条新增 Edge 代码为什么不能只通过组合完成？
- PR 是否新增或保留了 package patch，它的删除条件是什么？

## 范围

### 包含

- 精确上游基线 `0.1.1-rc.1`。
- 上游 DeepSeek catalog 中的 V4 Flash、V4 Pro 和 V4 Flash Vision Exp。
- 上游模型选择 UI 与 session 模型协议。
- 上游图片 composer、预览、历史 gallery、lightbox、wire types、session `ImageBlock`、准入词汇和 provider 转换。
- 上游 `AttachmentStore` 的 Edge 实现。
- 新的永久账号安装使用私有 R2 对象存储。
- 临时账号预览使用有界的 Durable Object 附件后端。
- 安装器与 Edge 诊断展示选定的附件后端。
- 使用真实产品素材、产品优先的中英文根 README。

### 不包含

- 通用文件、音频、视频、assistant 生成图片和公开附件 URL。
- 引用感知的垃圾回收；上游也因为恢复和 fork 的 session 可能共享不可变对象而暂缓该能力。
- 将已 claim 临时部署的 DO 附件自动迁移到 R2。Claim 后继续保留 DO 后端；未来显式迁移不能让已有引用失效。
- `web_fetch`、`@file`、`@session`、更多 provider 和无关的上游功能。
- 由 dsh-edge 维护第二套模型 catalog、附件 schema、composer、gallery 或 provider request serializer。

## 阶段 0 证据

### 已发布基线

- 审计的上游 tag 是 [`dsh-v0.1.1-rc.1`](https://github.com/deepseek-ai/deepseek-harness/tree/dsh-v0.1.1-rc.1)，commit 为 `528c682e061696f5a160f363f236ecbf53cbd006`。
- 相关 `@deepseek-ai/dsh-*` package 都已以精确版本 `0.1.1-rc.1` 公开发布；实现必须消费这些产物，而不是上游 checkout。
- rc.8 与 rc1 的 `SESSION_FORMAT_VERSION` 都是 `0`。图片消息增加的是上游 `ImageBlock`，不要求 Edge fork session 格式。

### 模型与 provider 链路

- `@deepseek-ai/dsh-llm-deepseek` 维护默认 catalog。不提供自定义 `models` 数组时，会按顺序暴露 `deepseek-v4-flash`、`deepseek-v4-pro` 和具备图片输入能力的 `deepseek-v4-flash-vision-exp`。
- 当前 Edge adapter 用 `models: []` 压掉了这个上游 catalog；阶段 1 应删除这个抑制，而不是维护本地模型列表。
- 上游 `DeepSeekAdapter` 已接受 `resolveAttachments` hook。它通过 `AttachmentStore` 解析并校验持久图片引用、转成临时 data URL、拒绝给纯文本模型发送图片，并执行上游 20 MiB 请求图片预算。dsh-edge 不得重复实现这个 serializer。
- 现有 request-scoped credential 与新路径兼容：Edge adapter 可以在活动 turn 中同时提供 API key 和 attachment resolver，二者都不持久化 secret 或 bearer 内容。
- 2026-08-21，使用 `deepseek-v4-flash-vision-exp` 向 `https://api.deepseek.com/chat/completions` 发起真实非流式请求，返回 HTTP 200，并将上游确定性的 1×1 红色 PNG 识别为 `Red`。临时测试 key 只传给该进程，没有写盘或写入本文档。
- DeepSeek 官方[模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)和 [Create Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion)目前仍只列 Flash 与 Pro。因此 0.3 会把 Vision Exp 标记为实验能力，并如实显示 provider 拒绝，不宣称所有账号都已经开放。

### 附件链路

- `@deepseek-ai/dsh-attachment` 是上游 seam。`AttachmentStore` 维护 `imageLimits`、`validateImage`、`saveImages`、`saveImage` 和 `readImage`；`admitEncodedImages` 负责规范 base64 和批量准入。
- 上游引用是不可变、内容寻址的 `sha256:` 标识，包含经过校验的媒体类型、字节数、宽、高和可选展示名。Session event 只保存这些引用，从不保存路径、object URL、provider URL 或 base64。
- `@deepseek-ai/dsh-client-ui-conversation` 负责粘贴/拖拽入口并读取 `imageLimits` projection；`@deepseek-ai/dsh-client-ui-attachment` 负责 draft rail、drop overlay、历史 gallery 和 lightbox。rc1 Web roster 已经包含附件插件；后端完成组合后，dsh-edge 应停止排除它。
- 上游 API 已定义 `session.attachment` wire shape、基于 session 引用的授权规则、模型模态预检和 `imageLimits` projection。由于 dsh-edge 已经拥有 Cloudflare 特定 `ApiProxy`，它只应对该现有 contract 做薄接线，复用上游类型、错误和准入 helper，而不是创建新 route 或 payload。
- `@deepseek-ai/dsh-attachment-local` 无法运行在 Workers：它依赖 Node filesystem/crypto 和原生 `sharp`。阶段 2 应实现上游 seam，而不是 patch 本地后端。Worker 兼容的完整图片校验及其对 Direct bundle size 的影响，是开启上传前必须验证的主要风险。

### 存储选择

- R2 是正式环境二进制的标准后端：object key 由上游 SHA-256 attachment identity 推导；Bucket 保持私有，只通过 Worker binding 访问。DO 继续保存 session event 及其上游引用。
- R2 Standard 有月度免费额度，但要求永久 Cloudflare 账号开通 R2 subscription。参见 [R2 开始使用](https://developers.cloudflare.com/r2/get-started/)和 [R2 定价](https://developers.cloudflare.com/r2/pricing/)。
- Cloudflare [临时账号支持资源列表](https://developers.cloudflare.com/workers/platform/claim-deployments/#supported-resources)包含 Workers、Static Assets、KV、D1、Durable Objects、Hyperdrive、Queues 和证书，但没有 R2。因此临时安装不能把 R2 作为强制依赖。
- 不使用 KV 做 fallback，因为附件上传之后需要立刻由模型读取，而 Workers KV 不保证 read-after-write，可传播 60 秒甚至更久。参见 [KV 一致性](https://developers.cloudflare.com/kv/concepts/how-kv-works/#consistency)。
- 临时 DO 后端是刻意限定的预览 fallback，不是长期对象存储架构。它的限制必须保守、不得超过上游准入限制，并且要显示在 Edge 诊断中。

### rc1 patch 处理结论

| rc8 patch | 阶段 0 结论 |
| --- | --- |
| `dsh-client-ui-conversation` 图片 gating | rebase 并保留，直到每种部署都组合 `AttachmentStore` 与 `imageLimits`；阶段 3 为临时预览补齐有界后端后删除，或等上游发布相同 capability gate 后删除 |
| `dsh-client-ui-workspace` 删除能力 | 除非 rc1 升级证明上游已有等价能力，否则 rebase 并保留；rc1 已发布代码中没有对应 gate |
| `dsh-host-apiproxy` Worker crypto | 基于实际 Worker bundle 重新审计；rc1 仍导入 `node:crypto` 且 UUID 调用点更多，不能机械沿用 rc8 patch |
| `dsh-llm` attribution manifest | 除非 bundler 可以不依赖运行时 `node:module` 消费已导出的 JSON，否则 rebase 并保留；rc1 仍使用 `createRequire` |
| `dsh-session-persistence` 有界读取与 abandon | rebase 并保留；rc1 未发布 Edge persistence adapter 所需的等价 coordinator API |
| `dsh-web-search-deepseek` redirect 处理 | rebase 并保留；rc1 仍使用没有通过 Worker 验证的 `redirect: "error"` |

阶段 0 没有证明任何新 patch 的必要性。rc1 基线保留六个 rebased patch；其中 conversation capability gate 会在临时预览尚无附件后端时继续保留。阶段 3 只有在所有部署都具备图片准入后才可删除它。可以依据 bundle 证据继续减少 patch，但不得静默扩大任何 patch。

## 阶段 1 证据

- 完整 standalone 与 `ui-edge` 依赖闭包已精确固定到 `0.1.1-rc.1`；根与 standalone lockfile 都只包含一个 Harness 版本。
- Edge 现在调用上游 DeepSeek `resolveAdapterOptions`，原样展示其 catalog：`deepseek-v4-flash`、`deepseek-v4-pro` 和 `deepseek-v4-flash-vision-exp`。没有新增 Edge 模型列表。
- 已发布的上游模型选择 client plugin 已进入经过审查的 30-plugin Web graph。Edge 现有 Cloudflare `ApiProxy` 把上游 LLM registry 投影到上游 `session.models`、`session.selectModel` 与 `llm.models` contract。
- Agent seam 仍是上游 `ModelSelectionRef`。一个 adapter 自有的 Durable Object KV 记录让已接受但尚未执行 turn 的 session 选择跨休眠保留；匹配的 canonical `request/header` event 持久 flush 后，该 KV 会在事务中退休。完成 turn 后，上游 event 仍是持久真源，没有修改上游 session table 或 event schema。
- rc1 结构化 boot 协议通过已发布的上游 `bootInjections`、`orderByModuleGraph` 和 `renderIndexInjections` 组装，没有维护 Edge 副本。
- 六个保留 patch 都已精确 rebase 到 rc1。host crypto patch 覆盖 rc1 增加的 UUID 调用点；没有新增 patch。只要 host 未投影 `imageLimits`，图片入口就继续保持 gated。
- 验证已通过：211 个单测、typecheck 与 lint；确定性 standalone 组装；30-plugin boot contract；浏览器 snapshot；Direct 与 Isolated 发布产物集成；已有发布版持久状态 fixture；Flash 与 Pro 文本路径；三模型发现；以及模型选择在 canonicalization 前后跨 Worker 重启。Direct 产物 gzip 为 690,801 bytes，预算为 921,600 bytes。

## 阶段 2 证据

- Edge 在私有 R2 上实现已发布的上游 `AttachmentStore` seam。Object key 来自上游 `sha256:` identity；R2 保存不可变原始字节，canonical session event 保持原样保存上游 image ref。没有增加 Edge attachment schema、公开 URL、composer、gallery 或 provider serializer。
- 现有 Edge `ApiProxy` 只接线上游 `admitEncodedImages`、错误 vocabulary、model-modality preflight、`imageLimits`、session-reference 授权和 `session.attachment`。请求作用域的上游 `DeepSeekAdapter` 仅收到一个调用已组合 store 的 resolver，因此 provider data-URL conversion 仍由上游拥有。
- 永久安装会创建或复用确定性的私有 R2 bucket，并仅把 binding 写入生成的部署配置；上传失败绝不会删除 bucket。R2 不可用时会给出可执行的启用/重试错误。临时预览在阶段 3 通过相同 seam 增加有界 DO backend 前，会刻意省略 `imageLimits`。
- Worker 侧 admission 会完整解码 PNG 与 JPEG，校验声明类型、尺寸、像素、字节、批次数量和总量，并且只声明这两种已经证明的格式。限额为每条消息 4 张、每张 3.5 MiB、合计 7 MiB、4,000 万像素，且单边不超过 2,000 像素。
- 已删除 standalone attachment-plugin exclusion，因此确定性的上游 Web graph 包含全部 31 个 plugin。现有精确版本 conversation capability patch 仍是六个 patch 之一：投影 `imageLimits` 时保留上游附件 UI，无后端的临时预览中只阻止粘贴/拖拽。Browser coverage 同时证明两条路径、草稿 admission、历史图片渲染和上游 Vision 模型标签。
- 验证通过：217 项 runtime unit test、typecheck、browser/install/model snapshot、确定性 standalone 装配、带本地 R2 的 Direct 与 Isolated release-artifact integration、已授权与跨 session 读取、多页冷历史图片谓词、模型选择/admission 串行化、临时预览入口 gating、fork 复用、重启持久性、corruption rejection、cancellation 与从 tarball 安装的 smoke check。Direct artifact 为 709,714 gzip bytes，预算为 921,600 bytes。

## 各阶段详细验收

### 阶段 1——基线与模型

- 将完整 standalone 与 `ui-edge` 依赖闭包精确固定到 `0.1.1-rc.1`。
- 重建上游 client graph；除非 Edge 确实没有对应能力，否则接受上游 roster 变化。
- 删除 `models: []`，模型元数据来自上游 adapter catalog。
- 让现有 Edge `session.models` 与 `session.selectModel` 直接展示和选择上游结果，不创建第二套 catalog。
- 在 attachment service 和权威 `imageLimits` 组合完成前继续关闭图片上传入口。
- 通过确定性装配、Direct 大小、两个 runtime 集成、浏览器 snapshot、包外安装和 rc8 持久状态 fixture。

### 阶段 2——在 R2 上运行上游附件

- 实现一个 Edge `AttachmentStore`；复用上游 ID、ref、limits、`AttachmentError` code、`admitEncodedImages`、UI、projection、wire payload、授权语义和 DeepSeek 转换。
- 原始不可变字节存进私有 R2 Bucket，session event 中不存图片字节。
- 在不信任浏览器 metadata、且不破坏 Direct gzip budget 的前提下，证明 Workers 中服务端 raster type/dimension/pixel 校验。
- 证明上传、prompt、授权历史读取、刷新、重启、fork/replay、损坏拒绝、取消和凭据不持久化。
- 安装器只为已认证且 R2 subscription 可用的账号创建或复用 Bucket；失败时明确给出恢复操作。

### 阶段 3——临时 fallback

- 只对没有 R2 binding 的部署，用有界 DO chunks 实现同一个 `AttachmentStore` contract。
- 存储选择发生在部署层，附件 seam 之上的代码无感知。
- Claim 临时部署后保留 DO 数据与后端；已认证升级不得静默切换存储而使历史失效。
- 诊断展示 `R2` 或 `Temporary DO`、限额、claim 后果和未来显式 R2 迁移路径。
- 匿名安装无需 Cloudflare 登录即可完成一个真实图片回合。

### 阶段 4——README 与发布

根 README 采用 [Wake](https://github.com/iAmCorey/Wake) 所展示的产品优先层次：badges、一句具体定位、用户问题与产品答案、真实产品素材，然后才是功能与安装。架构应放在后面或 runtime reference 中。

第一屏应让用户大约十秒内回答：

- dsh-edge 是什么？
- 相比本地运行 Harness，它为什么有用？
- 没有服务器、仓库或现成 Cloudflare 账号能否体验？
- 哪条命令开始安装？

README 必须按以下顺序组织：

1. 名称、release/npm/license/CI badges，以及独立社区项目身份。
2. 产品承诺：“一条命令，把 DeepSeek Harness 部署到你的 Cloudflare，在任何浏览器里使用。”
3. 一个具体的问题/解决方案段落，以及真实 screenshot 或经过优化的短动画。
4. `npx dsh-edge install`，并说明临时与永久安装的区别。
5. 用户收益：随处访问、自己的 key/data、Web Search、workspace/shell、三款模型和实验性图片理解。
6. Runtime 与附件存储选择、安全、限制、升级，然后才是开发和架构。

中英文具有同等权威。产品表述必须与测试行为一致；README 必须说明临时部署不 claim 会过期、永久图片存储需要启用 R2，并且 Vision Exp 是否可用可能取决于 provider 账号。
