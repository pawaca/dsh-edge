## 已采用的决策

- D1：只向原会话投递；任务与历史保留在 SQL，继续由 DO alarm 驱动。新 Host ID 编码旧的会话/任务复合键，无需重写历史。活跃和暂停合计最多 128 条，已结束最多 128 条；历史仍为每任务 200 条/30 天。手动运行不消耗下一次计划，队列中或执行中的同任务拒绝再次运行。
- D2：每跳 URL 限制和 Workers fetch 保留；严格公共网络标志是平台边界，URL 检查不等于 DNS 固定。
- D3：Markdown 复制在读取行内容前预检，最多 2,048 个事件、4 MiB 存储载荷；解码后 JSON 和最终 UTF-8 输出再次限制在 4 MiB。超限 413，引导使用已有流式日志下载。
- D4：保留 Trajectory，原始 JSON 仅在当前 Session 生命周期内可用。单结果 256 KiB、单会话 1 MiB、全局 4 MiB、每会话 128 条、最多 16 个 follower；超限、驱逐、冷会话和会话销毁均为 unavailable。
- D5：实现 patchText/deleteFile/moveFile 与删除意图记录。patch/move 文本上限 2 MiB；移动锁两个路径并保留换行及 mode，目标已发布但源删除失败明确报告部分成功。apply_patch 不启用。
- D6：继续启用先读后写策略，与上游新默认不同。
- D7：精确锁定 rc.1。alpha staging 验收和 0.35.0 正式发布已完成；发布没有升级现有部署。

## 存储、内存与回滚边界

新任务元数据和上传回执使用可空新增列；不为升级全表回写记录。日程列表只读最多 256 条任务；执行状态通过队列唯一索引定位，不扫描会话日志。deleteRecords 在同一事务内按实际键数分批；含 sidecar 时每批最多 64 条记录。

Markdown 只读固定大小的预检页。格式化的瞬时对象和字符串会放大存储载荷，4 MiB 输入并不等于 4 MiB 峰值堆。Trajectory 另有限制遍历深度、节点数量和 follower 数量；UTF-16 字符串和 JSON 解码对象同样有额外开销。下文记录本地 workerd 并发 Markdown 的堆采样；不以静态上限宣称测得整个 isolate 的峰值，组合负载仍需 staging 证据。

V4 不代表可以直接降级：新 RRULE 任务和不带 parentSession 但含继承投递确认的新分叉，可能不被旧版本理解。应升级前保存恢复点；降级应恢复升级前状态，不能仅替换 Worker 二进制。本文不授权任何线上恢复操作。

## 本地 DB 与 alarm 突发请求验收

用同一份本地 provider 测试数据，对比优化前、后的 rc.1 本地候选预构建产物。这组突发测试不是上面的 0.34.0 对照。20 次列表读取分为五波，每波四个并发请求；128 个任务各保留一条投递回执。读取计数前用 readiness 请求刷出遥测；热读取不混入冷启动。静置采样结束时不发 readiness 请求，避免测量本身唤醒 DO。SQL 行计数与 KV/alarm 操作次数分开记录。

| 场景 / 计数 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 128 次投递后读取首页 20 次：SQL 调用 | 2,580 | 40 |
| 同组读取：SQL 读行 | 7,680 | 2,600 |
| 手动执行 128 次：alarm 回调 | 128 | 4 |
| 同组执行：setAlarm 调用 | 385 | 9 |
| 同组执行：SQL 读行 | 294,193 | 49,012–49,013 |
| 同组执行：SQL 写行 | 6,399 | 6,407 |

两种模式均复现优化后结果。最终候选在这组 128 次执行中多写 8 行 SQL（0.13%）；这些优化不会省掉必要的持久化写入。列表先分页，再批量按队列索引查询执行状态，不扫描投递或事件历史。常规下一任务查询读取已有 due 索引；队首暂停或重试时的回退最多检查 128 个活动任务。每次 alarm 最多接收 32 条输入，经过 5 秒后停止接收下一条；已接收的回合仍保留自己的截止时间。工作未完成时复用已有较早恢复闹钟，清空后重新对齐下一截止时间。这些优化不需要迁移或新索引。

任务页在全部 128 次执行期间保持打开，直接 cursor 计数为读取 82,648 行、写入 6,407 行、4 次 alarm 回调和 9 次 setAlarm；额外读取用于实时刷新任务列表。持续 Remote 连接的 traces 偶尔漏掉已完成回合，因此排除这些不完整采样。该场景把 Direct 预构建产物复制到临时目录，在存储方法外增加计数，并在执行和消费 cursor 后读取实际 workerd `SqlStorageCursor.rowsRead/rowsWritten`，另行计数 KV/alarm 操作，不保留结果载荷，不修改生产产物。无订阅对照的 SQL 调用、写行和 alarm 操作一致（读取 49,008 行，独立 spans 运行读取 49,012–49,013 行）。这些是本地观测，不是部署后的账单总量。

保留历史后的首页读取不写 SQL 或 alarm。最终 15 秒静置采样没有浏览器 HTTP/WS 或 DO 存储活动；这是有限窗口的观测，不是永久零成本承诺。队列探针另通过 20 个并发重复请求、128 条容量、取消、公平轮转与崩溃恢复；日程探针验证忙会话互斥、删除、重启后的持久 alarm 投递和不重复执行。

模型目录保留 TTL、过期后后台刷新、凭据隔离和单次刷新合并，改为访问时刷新，不使用后台定时器。版本绑定补丁具备去除补丁即失败的测试：空闲时推进时钟不能再次请求 provider；20 个并发访问共享一次加载，失败后仍遵守 TTL。去掉这个定时器本身不代表整个 DO 已证明可休眠。

## 本地空闲生命周期回归

此前 300 秒测试失败的根因已确定：`commands/list` 请求完成后，仍保留无法主动取消的十分钟 `AbortSignal.timeout` 定时器。现在用请求作用域管理截止时间，操作成功或失败后立即清除定时器，保留正在执行时的超时和调用方取消语义。同一生命周期规则覆盖普通 RPC、命令排队、MCP 请求与 OAuth 操作。

最终两个预构建模式均通过 30 秒空闲浏览器回归：静置后发送消息，观察到 carrier 重建，并通过恢复后的订阅收到完成回复。该回归已默认纳入快照套件。单测同时要求成功/失败 RPC 结束后计时器归零，活动请求的超时与取消仍然有效。本地失败已关闭。后续有限 staging 测试也已观察到附件恢复和 alarm 触发重建，见当前正式版说明。

## 本地大内容内存采样（2026-11-09）

新增复制路径现在有覆盖整个响应的并发限制。`MarkdownCopyBudget` 每个 DO 仅允许一个格式化/响应体，通过 16 KiB 分块保持背压，在完成、失败、调用方取消或 30 秒截止时释放名额。额外请求在读取 SQL 和格式化之前返回 429。单测覆盖 32 个重叠请求、停滞读取、取消和格式化失败，防止独立的 4 MiB 快照及响应体随请求不断累积。

`content-memory.probe.mjs` 每 20 ms 采样预构建 Direct workerd 的 V8 堆。provider 测试程序可按请求 UTF-8 字节数除以四返回估算输入 usage，驱动真实上游 token 压力和压缩代码；这不是生产 tokenizer usage，也不是实际 provider 验证。短阶段只有 2–3 个采样，因此记录的是观测最大值，不是瞬时峰值或存活堆保证。

| 场景 | 候选观测 |
| --- | --- |
| 44 回合历史的 32 个冷启动复制 | 成功内容各 1,901,981 bytes，其余返回 429；采样堆 48.7 MiB |
| 6 个会话各进行 20 次真实文件读取 | 累计产生约 6.6 MB 原始结果；最早结果不可用、最新结果可用，验证全局淘汰；采样堆 144.2 MiB |
| 驻留历史/结果 + 16 个订阅 + 32 个复制 + 流式上传 16 MiB | 复制准入和上传成功；采样堆 141.9 MiB，独立 backing storage 最大值 56.1 MiB |
| 保持上述驻留会话，继续至 80 个长回合 | 采样堆 170.1 MiB |
| 32 个冷启动超限复制 | 在加载完整历史前全部返回 413；采样堆 54.9 MiB |

按请求大小返回 usage 的 100 回合对照中，两版均触发一次真实上游自动压缩：候选采样堆最大值 127.1 MiB，npm 0.34.0 为 125.0 MiB；冷恢复分别为 64.4 和 67.8 MiB。旧版本没有新增 Trajectory 缓存，构造六个驻留工具会话时仍达到 146.9 MiB，继续长历史后达到 172.9 MiB。GC 时机不同，不能把这些数据当作精确的相对内存基准。

**0.35.0 保留的已知容量风险。** 这些采样识别了原有驻留历史压力和已修复的新增复制无界并发，不能证明低于 [Cloudflare 内存限额](https://developers.cloudflare.com/workers/platform/limits/)。堆与 backing storage 的最大值不能相加，GC 时机不同也无法得出精确的相对内存结论。后续有限 staging 验收已通过，包括附件与日程 alarm 触发的冷重建；这不证明最坏容量，也不构成安全历史长度或会话数量阈值。两版共同的重负载容量风险独立于本次基线升级跟踪；本次发布不包含全面重做 Agent 驻留策略或实现恢复工具。公网抓取已通过；私网 DNS 解析边界、各账户预算和可执行恢复流程仍需按部署核对。

升级前历史观察（2026-11-09）：只读核对指定 staging Worker 为 Edge 0.34.0-alpha.1 / Harness 0.2.1-rc.4，Container 模式，temporary-do 附件后端。针对这个精确已发布版本的补充本地探针通过全部 11 项原位状态升级检查；九个普通回合 SQL 写入为候选 441 行、旧版 443 行，KV/alarm 写操作均为 36。这些探针使用本地测试状态，不是 staging 用户数据。随后同版本 alpha 镜像已发布，有限 staging 验收已完成，最新结果见顶部正式版说明。

## 复现本地资源检查

构建并提升两个 Worker 后，从 `apps/dsh-edge` 目录执行：

```sh
node tests/resource-cost.probe.mjs
DSH_EDGE_TEST_RUNTIME_MODE=isolated node tests/resource-cost.probe.mjs
DSH_EDGE_WATCH_TASKS=1 node tests/resource-cost.probe.mjs
DSH_EDGE_COST_CURSOR=1 node tests/resource-cost.probe.mjs
DSH_EDGE_MEMORY_USAGE=estimate DSH_EDGE_MEMORY_COPIES=32 DSH_EDGE_MEMORY_SATURATE=1 node tests/content-memory.probe.mjs
DSH_EDGE_MEMORY_USAGE=estimate DSH_EDGE_MEMORY_HISTORY_ONLY=1 node tests/content-memory.probe.mjs
```

任务页订阅场景自动使用 cursor 计数；`DSH_EDGE_COST_CURSOR=0` 可强制使用 spans 做诊断。计数器重置或缺少回合 checkpoint 时，探针直接失败，不把漏报写成成本改善。可通过 `DSH_EDGE_PROBE_REPORT` 保存 JSON。这些命令不读取生产数据，也不部署 Worker。
