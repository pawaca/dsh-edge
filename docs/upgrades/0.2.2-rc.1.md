# DeepSeek Harness 0.2.2-rc.1 baseline adaptation

Status updated 2026-11-10: Edge 0.35.0 is published on npm latest, with its matching git tag, GitHub Release and Container image. It promotes the published and staging-tested 0.35.0-alpha.1 runtime. Starting point: Edge 0.34.0 / Harness 0.2.1-rc.4. Bounded functional, native UI, attachment and alarm-triggered cold-recovery acceptance passed; local DB/alarm regression checks passed. Long-history memory remains a disclosed capacity risk, not a demonstrated upgrade regression. See the [0.35.0 release notes](../releases/0.35.0.md) for current evidence and limits. The 2026-11-09 sections below retain the historical candidate measurements and then-open gates; their staging status is superseded by this update. Production deployment still requires an account-budget check and a usable recovery process; new recovery tooling is outside this release.

## Adopted decisions

- D1: deliver only to the original Session; keep SQL tasks/history and DO alarms. New Host IDs encode the legacy Session/task composite key without rewriting history. Active plus paused tasks are capped at 128, ended tasks at 128; history remains 200 records / 30 days per task. Manual run leaves the next occurrence intact and refuses an already queued/running execution of that task.
- D2: retain per-hop URL policy and Workers fetch. The strictly-public platform flag supplies the network boundary; URL validation does not pin DNS.
- D3: preflight Markdown rows before loading payloads, with 2,048 events / 4 MiB stored payload. Recheck decoded JSON and final UTF-8 output at 4 MiB. Overflow returns 413 and points to the existing streaming log download. One copy per DO holds admission through response completion, cancellation or a 30-second deadline; concurrent excess returns 429 with Retry-After before storage reads.
- D4: retain Trajectory and live-only raw JSON: 256 KiB per result, 1 MiB per Session, 4 MiB globally, 128 results per Session and 16 followers. Oversized, evicted, cold and disposed results are unavailable.
- D5: implement patchText/deleteFile/moveFile and delete-intent capture. Patch/move text is capped at 2 MiB; moves lock both paths, preserve line endings/mode and explicitly report a published destination whose source removal failed. apply_patch stays disabled.
- D6: retain read-before-write observation policy, differing from the new upstream default.
- D7: pin rc.1 exactly. Alpha staging acceptance and stable 0.35.0 publication are complete; publication did not upgrade existing deployments.

## Storage, memory and rollback boundaries

Task metadata and upload receipts use additive nullable columns without upgrade-time full-table rewrites. The task list reads at most 256 tasks; execution checks seek the queue unique index without scanning Session history. deleteRecords batches actual storage keys in one transaction: at most 64 records per batch when sidecars are included.

Markdown reads a fixed preflight page. Formatter objects and strings amplify stored bytes: 4 MiB input is not a measured 4 MiB heap peak. Trajectory also caps traversal depth, node count and followers; UTF-16 strings and decoded JSON add overhead. Local workerd heap samples for concurrent Markdown requests are recorded below. Static caps are not presented as measured whole-isolate peaks; combined workloads still need staging evidence.

V4 does not imply safe binary-only downgrade: new RRULE tasks and parentless ordinary forks carrying inherited delivery acknowledgments may not be readable by the old baseline. Preserve a recovery point before upgrading; downgrade by restoring pre-upgrade state, not merely swapping the Worker binary.

## Local DB and alarm burst acceptance

Compare the previous local rc.1 candidate with this optimized candidate, using the same promoted workerd artifacts and local provider fixture. These burst numbers are not the 0.34.0 comparison above. Twenty list reads run in five waves of four concurrent requests; 128 tasks retain one receipt each. Readiness requests flush telemetry before counters are sampled; warm reads exclude cold activation. Parked-idle measurements omit the trailing readiness request, which would itself wake the DO. SQL row counters and KV/alarm operation counters are reported separately.

| Scenario / counter | Before | After |
| --- | ---: | ---: |
| 20 first-page reads after 128 deliveries: SQL calls | 2,580 | 40 |
| Same reads: SQL rows read | 7,680 | 2,600 |
| 128 manual executions: alarm callbacks | 128 | 4 |
| Same executions: setAlarm calls | 385 | 9 |
| Same executions: SQL rows read | 294,193 | 49,012–49,013 |
| Same executions: SQL rows written | 6,399 | 6,407 |

Both modes reproduce the after result. The final candidate adds 8 SQL row writes (0.13%) in this 128-execution workload; it does not eliminate persistence writes. The list slices before resolving execution state, batches keyed queue lookups, and never scans delivery or event history. The common next-task lookup reads the existing due index; paused/retrying heads use a fallback bounded by 128 active tasks. One alarm admits at most 32 inputs and stops admitting after 5 seconds; each already admitted turn retains its deadline. Existing earlier recovery alarms are reused while work is pending, then reconciled after draining. No migration or new index is needed for these optimizations.

With the task page visible during all 128 executions, direct cursor counters measure 82,648 rows read, 6,407 rows written, 4 alarm callbacks and 9 setAlarm calls. Extra reads serve live task-list updates. Long-lived Remote traces intermittently omitted completed turn spans, so those incomplete samples are rejected. For this scenario the probe copies the promoted Direct artifact into a temporary directory, wraps storage methods, and reads actual workerd `SqlStorageCursor.rowsRead/rowsWritten` after execution and cursor consumption. It counts KV/alarm operations separately, retains no result payloads, and changes no production artifact. The unwatched control agrees on SQL calls, writes and alarm operations (49,008 rows read, versus 49,012–49,013 in the separate span runs). These are local observations, not deployed billing totals.

Browsing a retained first page writes neither SQL nor alarms. The final 15-second parked samples show no browser HTTP/WS or DO storage activity; this is a bounded observation, not a promise of permanent zero cost. The queue probe also passes 20 concurrent duplicate retries, 128-input capacity, cancellation, fair rotation and crash/restart recovery. The schedule probe verifies busy-session exclusion, deletion and persisted-alarm delivery without duplication.

Model discovery retains TTL, stale-while-refresh, credential scoping and single-flight but refreshes on access rather than a background timer. The version-bound provider patch has a failing-without check: advancing an idle clock must not issue another provider request; 20 concurrent accesses share one load and a failed refresh retains its TTL. Removing that timer alone does not prove whole-DO hibernation.

## Local idle lifecycle regression

The former 300-second failure had a concrete cause: completed `commands/list` requests left an uncancellable ten-minute `AbortSignal.timeout` timer alive. A request-owned deadline now clears its timer when the operation succeeds or fails, preserving expiry and caller cancellation for active work. The same lifetime rule covers ordinary RPCs, command admission, MCP requests and OAuth operations.

Both final promoted modes pass the 30-second idle browser regression: after idle, a prompt causes carrier replacement and a completed reply through restored subscriptions. The regression is enabled in the default snapshot suite. Unit tests also require zero timers after completed/failed RPCs and preserve active-work timeout/cancellation. This closes the local failure. Subsequent bounded staging tests also observed attachment recovery and alarm-triggered reconstruction; see the current release notes.

## Local large-content memory samples (2026-11-09)

The new copy path now has a whole-response concurrency bound, not only a byte bound. `MarkdownCopyBudget` admits one render/body per DO, emits 16 KiB chunks for backpressure, and releases on completion, failure, caller cancellation or a 30-second deadline. Excess demand returns 429 before SQL or formatting. Unit tests cover 32 overlapping calls, stalled readers, cancellation and renderer failure. This prevents requests from accumulating independent 4 MiB snapshots and response bodies.

`content-memory.probe.mjs` samples the promoted Direct workerd V8 heap every 20 ms. The provider fixture can report request UTF-8 bytes divided by four as estimated input usage, exercising actual upstream token-pressure/compaction code; it is not production tokenizer usage or a real-provider test. Short phases have only 2–3 samples, so these are observed maxima, not instantaneous or live-retained heap guarantees.

| Scenario | Candidate observation |
| --- | --- |
| 32 cold copies of a 44-turn history | Successful copies are 1,901,981 bytes; excess receives 429; sampled heap 48.7 MiB |
| 6 Sessions × 20 real file reads | About 6.6 MB raw results produced; oldest unavailable and newest available prove global eviction; sampled heap 144.2 MiB |
| Resident history/results + 16 followers + 32 copies + streamed 16 MiB upload | Copy admission and upload succeed; sampled heap 141.9 MiB; separate backing-storage maximum 56.1 MiB |
| Continue to 80 long turns with those resident Sessions | Sampled heap 170.1 MiB |
| 32 cold oversized copies | All 413 before full-history loading; sampled heap 54.9 MiB |

The controlled 100-turn request-sized-usage scenario triggered one real upstream compaction on both versions: candidate heap maximum 127.1 MiB versus 125.0 MiB on npm 0.34.0; cold resume was 64.4 versus 67.8 MiB. The released version also reached 146.9 MiB while constructing six resident tool Sessions and 172.9 MiB after continuing the long history, without the new Trajectory cache. Different GC timing prevents treating this as a precise relative-memory benchmark.

**Known capacity risk retained in 0.35.0.** These samples identify pre-existing resident-history pressure and the newly fixed unbounded copy concurrency; they do not prove safety below the [Cloudflare memory limit](https://developers.cloudflare.com/workers/platform/limits/). Heap and backing-storage maxima are not additive, and different GC timing prevents a precise relative-memory conclusion. Bounded staging acceptance subsequently passed, including attachment and alarm-triggered cold reconstruction. It does not establish worst-case capacity or a safe history/session-count threshold. The shared heavy-load capacity risk is tracked separately from this baseline promotion; no general Agent-retention redesign or recovery-tool implementation is part of the release. Public web fetching passed; private-resolving DNS boundaries, per-account budget and an operational recovery process remain deployment-specific concerns.

Historical pre-upgrade observation (2026-11-09): the designated staging Worker was read-only verified as Edge 0.34.0-alpha.1 / Harness 0.2.1-rc.4 in Container mode, using temporary-do attachments. Additional local probes against that exact published version pass all 11 in-place state-upgrade checks. Nine ordinary turns write 441 SQL rows versus 443 on that baseline, and KV/alarm writes are 36 on each. These probes use local fixture state, not staging user data. The matching alpha image was subsequently published and bounded staging acceptance completed; see the current release notes above.

## Reproducing the local resource checks

After building and promoting both Workers, run from `apps/dsh-edge`:

```sh
node tests/resource-cost.probe.mjs
DSH_EDGE_TEST_RUNTIME_MODE=isolated node tests/resource-cost.probe.mjs
DSH_EDGE_WATCH_TASKS=1 node tests/resource-cost.probe.mjs
DSH_EDGE_COST_CURSOR=1 node tests/resource-cost.probe.mjs
DSH_EDGE_MEMORY_USAGE=estimate DSH_EDGE_MEMORY_COPIES=32 DSH_EDGE_MEMORY_SATURATE=1 node tests/content-memory.probe.mjs
DSH_EDGE_MEMORY_USAGE=estimate DSH_EDGE_MEMORY_HISTORY_ONLY=1 node tests/content-memory.probe.mjs
```

The watched scenario automatically uses cursor instrumentation; `DSH_EDGE_COST_CURSOR=0` forces spans for diagnostics. A counter reset or missing turn checkpoint fails the probe instead of being reported as a cost improvement. `DSH_EDGE_PROBE_REPORT` optionally saves JSON. None of these commands uses production data or deploys a Worker.
