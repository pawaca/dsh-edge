## dsh-edge 0.17.0-alpha.1

First preview of two multi-step tools for the Isolated (Dynamic Worker) runtime: `workflow`, which orchestrates many subagents from one script, and `run_code`, which runs a TypeScript program that calls the other tools. Published to npm's `next` channel; `latest` remains on 0.16.0. Use this alpha on a test instance before upgrading a primary deployment. The upstream Harness baseline remains 0.1.5-rc.2.

### Added

- **Runtime providers** (#209): Direct Shell and Dynamic Worker are now modeled as runtime providers with capabilities and plan requirements. The Worker and the installer derive their runtime facts from the same catalog. A capability that only some providers offer is absent, not broken, where its provider is unavailable. There is no behavior change on its own.
- **`workflow` tool** (#210, Isolated only): the upstream `dsh-tool-workflow` orchestration tool. The model writes a script with `agent()`, `parallel()`, `pipeline()`, `phase()` and `log()` that fans work out across subagents.
  - Each run executes its script in its own Dynamic Worker, with no outbound network and a Worker Loader `cpuMs` limit. workerd forbids the in-process `eval`, `new Function` and `node:vm` that the upstream engine needs.
  - `agent()`, `phase()` and `log()` cross an RPC bridge. The Durable Object enforces the caps: at most 4 children at once and 100 per run. Request, reply, progress and result sizes are bounded as well.
  - Cancelling the turn disposes the isolate and cancels the children.
- **`run_code` tool** (#211, Isolated only): upstream `dsh-tools` PTC mode, enabled as `both` so it sits alongside the native tools. The model writes a TypeScript program that calls tools as `await tools.name(args)`.
  - Types are stripped with sucrase, and each program runs in its own Dynamic Worker.
  - Every nested call is a normal tool dispatch, so approval and spill behave as usual.
  - Per run: at most 200 nested calls, 256 KiB of arguments per call, 2 MiB per result, and 1 MiB of total output.
  - The prompt carries a generated tool SDK section on every turn, which costs extra input tokens.

### Fixed

- **Turn context for isolate calls** (#212): calls from a workflow or code isolate back into the Durable Object now run inside the tool call that started them. Before this fix, a file tool called from `run_code` failed with "File operations are only available during an active turn".

### Limits

| Limit | workflow | run_code |
|---|---|---|
| Isolate CPU (`cpuMs`) | 30 s | 30 s |
| Concurrent children / nested calls | 4 | 4 |
| Children / nested calls per run | 100 | 200 |
| Wall clock | turn residency (10 min) | 5 min |
| Result | 1 MiB | 1 MiB total output |

### Validation and upgrade

`pnpm run check` passes 534 tests. Integration runs against both release artifacts: Direct asserts both tools are absent, and Isolated runs a 5-child workflow plus a `run_code` program that writes and reads a file. Local testing with a real model covered:
- 3- and 6-child workflows, including schema output and cancellation mid-run
- `run_code` with bash, file, `web_fetch` and approval
- history replay after a reload
- UI rendering

A 6-child workflow wrote about 135 session-event rows. Local workerd does not enforce `cpuMs`, so that limit is verified only in production.

Upgrade a test instance with `npx dsh-edge@next upgrade`. The new tools appear only on Isolated deployments; Direct deployments are unchanged. This release adds no new storage schema or migration.
